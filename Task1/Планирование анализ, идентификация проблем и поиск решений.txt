**Анализ схемы, идентификация существующих проблемных мест** 
1. Медленная загрузка первой страницы сервиса MES
- операторам важно видеть список заказов на этой странице, от этого зависят их выплаты
- внедрение пагинации и фильтров не решило проблему
- риски: возможные потери заказов, недовольство операторов

2. Клиенты не вовремя получают свои заказы
- клиентам важно получить заказ в означенный срок, в реальности клиент ждет заказ несколько месяцев вместо нескольких недель либо не получает вовсе
- нет понимания, на какой стадии происходит задержка, при этом на производстве проблем нет
- риски: потеря заказов, потеря клиентов

3. Медленная скорость расчета стоимости в MES
- средняя скорость расчета - 2-3 минуты, однако в случае сложной модели может вырасти до 30 минут
- риски: ухудшение UX

4. MES API открыт наружу
- судя по схеме, в этом случае будет синхронная обработка заказа на расчет
- риски: долгая обработка запроса, отсутствие защиты от DDOS-атак, потеря заказов в случае отказа

5. Ответственность за работу с заказом размазана по разным сервисам
- cтатус заказа могут менять несколько систем (MES, CRM, онлайн-магазин), по-хорошему работа с сущностью Заказ должна быть вынесена в микросервис работы с заказами
- риски: процесс оформления заказа по сути распределен по нескольким сервисам, сложности при исследовании проблем, когда заказ "застрял" где-то

6. Не реализован принцип Observability
- отсутствуют мониторинги для сервисов компании
- риски: сложности при расследовании проблем и инцидентов

7. Отсутствуют реплики нагруженных сервисов и БД
- не настроено реплицирование сервисов, невозможно распределять запросы и нагрузку по нескольким инстансам сервиса
- риски: отказ в случае превышения нагрузки, потеря заказов, потеря клиентов

8. Отсутствует автоматизированный прогон регресс-кейсов при тестировании
- тестировщик вручную прогоняет E2E-тесты, в случае нахождения критичных багов релиз откладывается на неопределенное время
- риски: высокий bus-фактор (тестировщик один в компании), увеличение TTM

**Инициативы, которые необходимы для устранения нежелательных ситуаций**
1. Для устранения долгой загрузки первой страницы MES необходимо проанализировать текущую ситуацию. Скорее всего, "тормоза" возникают на уровне БД. Предлагается: 
- провести аудит текущих медленных запросов. Возможно, будет достаточно добавить индексов
- провести оптимизацию запросов
- рассмотреть вариант реализации read-реплики для БД
- добавить кэширование для заказов с внедрением Redis

2. Для понимания причин, почему клиенты не получают вовремя заказы, предлагается: 
- внедрить системы мониторинга и алертинга
- добавить дашборды с отображением бизнес-метрик (например, количество заказов в конкретных статусов, время нахождения в текущем статусе и тд)
- внедрить хранение истории заказов (кто взял заказ в работу, когда, в каком статусе и тд), т.к. необходим аудит 

3. Для улучшения опыта работы с MES предлагается: 
- внедрить кэширование расчета некоторых стандартных моделей (если таковые предлагаюся на сайте). Если таковых нет, можно провести анализ самых популярных моделей, которые подаются на расчет, выбрать какой-то топ таких моделей, и расчет таких моделей хранить в кэше. При изменении тарифов на расчет проводить перерасчет (фоновая операция), после чего инвалидировать кэш расчетов таких "стандартных" моделей
- в случае наличия ресурсов можно провести аудит кодовой базы MES на предмет возможных улучшений для оптимизации скорости расчета моделей

4. Необходимо устранить синхронное взаимодействие партнеров с MES API. Предлагается: 
- внедрить асинхронную работу, заказы должны поступать в очередь заказов. Далее требуется анализ, возможные варианты: 
  - выдача партнеру уникального гуида заказа, далее партнер можно получать статус заказа по этому номеру
  - запись сообщения в очередь об успешном расчете, партнер считывает его
  - внедрение коллбэков или пушей для уведомления партнера об успешном расчете
- внедрить API gateway 
- настроить firewall для запросов из внешней сети

5. Предлагается в перспективе реализовать единый сервис по работе с заказами, что позволить локализовать логику работы с заказами, что улучшит поиск причин каких-то проблем со статусами или потерей заказов

6. Предлагается реализовать observability-принцип для сервисов компании, что позволит быстро реагировать на возможные инциденты, выход из строя сервисов или БД

7. Предлагается реализовать реплики для сервисов и БД, что позволит более плавно распределять нагрузку, быть лучше готовыми к пиковым нагрузкам

8. Предлагается внедрить автоматические прогоны E2E-сценариев в пайплайны, проходящие еще на dev-среде. Также предлагается автоматизировать вывод на release-среду в случае успешного прохождения тестов. Необходимо также реализовать прогон smoke-тестов на продакшн-среде. 

9. Предлагается также реализовать кэширование для элементов, которые используются для работы с конструктором при сборке 3D-модели на сайте компании.

10. Предлагается также открыть вакансию на найм QA-специалиста для устранения bus-фактора. В случае ухода текущего QA будет большая потеря экспертизы. Кроме того, список инициатив потребует зайдействования минимум двух QA.

**Приоритизация инициатив**

Выбор 3 инициатив для реализации в ближайшее время: 
1. Настройка мониторинга и алертинга. Самый критичный момент, т.к. на текущий момент заявлено о проблемах потери заказов и их "застревания". Внедрение такой системы позволить оперативно видеть текущие проблемы и облегчит анализ проблем и инцидентов. 
2. Устранение долгой загрузки первой страницы MES. Также критичный момент, т.к. напрямую влияет на сотрудников компании (операторов), которые могут потерять в деньгах, и на клиентов, которые по итогу могут дольше ждать свои заказы.
3. Устранение синхронного взаимодействия с MES API для партнеров. Потенциально это уявзимость, которую могут использовать конкуренты или злоумышленники, в результате атаки на которую может лечь вся система компании, станут невозможны расчеты.
