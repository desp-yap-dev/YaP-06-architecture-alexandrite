# Мотивация

**Текущая ситуация:**
- Яндекс Метрика подключена к сайту, но не покрывает API-интеграции, которые стали критичными для бизнеса
- Нет мониторинга компонентов IT-ландшафта компании
- Проблемы обнаруживаются только по жалобам клиентов и партнеров
- Отсутствие данных о производительности системы затрудняет принятие решений по оптимизации

**Внедрение мониторинга позволит:**
- снизить количество потерь заказов
- снизить количество потерь клиентов
- повысить прозрачность системы, бизнес-метрики позволят в режиме реального времени понимать текущее состояние системы
- быстрее анализировать проблемы и инциденты, тем самым экономя время команды на реализацию новых фич
- видеть рост нагрузки, позволяя заранее планировать масштабирование системы
- своевременно получать уведомления о проблемах в работе компонентов системы и оперативно реагировать на них

# Выбор подхода к мониторингу
Предлагается использовать разные подходы для разных частей системы. <br /><br />
1. Для сервисов, предоставлящих API, предлагается использовать подход RED: MES API, CRM API, Shop API. Подход RED наилучшим образом подходит, когда необходимо анализировать сервисы, которые управляеются запросами. <br />
- R - количество запросов в секунду. Позволит понимать текущую нагрузку. 
- E - количество ошибок. Увеличение данной метрики позволит понять, что что-то нарушилось в работе системы. 
- D - длительность. Ухудшение данной метрики позволит понять, что что-то нарушилось в работе системы. <br />

2. Для серверных компонентов системы (сервисы, бд, очереди) предлагается использовать подход USE. Данный подход лучше подходит для инструментов, производительность которых ухудшается с ростом нагрузки. <br />
- U - позволит понять загрузку ресурса (CPU, RAM)
- S - позволит понять, перегружен ли ресурс (задержки)
- E - ошибки

3. Для бизнес-метрик предлагается использовать подход 4 золотых сигнала. Например: <br />
Задержка - среднее время на обработку заказа<br />
Трафик - количество заказов <br />
Ошибки - количество ошибок при обработке заказов <br />
Насыщенность - наличие очереди из заказов, время ожидания перехода из начального статуса<br />

# Отслеживаемые метрики
### 1. Сервисы API
- Number of requests (RPS) for internet shop API - покажет нагрузку на API магазина. Рещкий рост или резкое падение (настройка через алертинг) - повод посмотреть логи приложения. Ярлыки: 
  - method
  - status code
- Number of requests (RPS) for CRM API - покажет нагрузку на CRM. Важно, поскольку в CRM работают продавцы, там в т.ч. формируются заказы. Ярлыки: 
  - method
  - status code
- Number of requests (RPS) for MES API - покажет нагрузку на MES со стороны партнеров. Важно, поскольку при отказах можем потерять заказы от партнеров. Ярлыки: 
  - method
  - status code
  - partner login
- Number of requests (RPS) per user for MES API - покажет нагрузку на MES API в разрезе партнеров. Резкий рост по конкретному партнеру может отразить проблему с интеграцией. Ярлыки: 
  - partner login
  - url
- Response time (latency) for shop API - покажет время ответа для пользователей магазина. Критично для UX. Ярлыки: 
  - method
  - status code
- Response time (latency) for CRM API - покажет время ответа для продавцов. Критично для UX. Ярлыки: 
  - method
  - status code
- Response time (latency) for MES API - покажет время ответа для партнеров. Критично для интеграции. Ярлыки: 
  - method
  - status code
  - partner login
- Number of HTTP 200 for shop API - покажет количество успешных ответов от магазина. Отражает общую работоспособность магазина. Ярлыки: 
  - method
  - status code
- Number of HTTP 200 for CRM API - покажет количество успешных ответов от CRM. Отражает общую работоспособность CRM. Ярлыки: 
  - method
  - status code
- Number of HTTP 200 for MES API - покажет количество успешных ответов от MES. Отражает общую работоспособность MES. Ярлыки: 
  - method
  - status code
  - partner login
- Number of HTTP 500 for shop API - покажет количество неуспешных ответов от магазина. Отражает общую работоспособность магазина. Ярлыки: 
  - method
  - status code
- Number of HTTP 500 for CRM API - покажет количество неуспешных ответов от CRM. Отражает общую работоспособность CRM. Ярлыки: 
  - method
  - status code
- Number of HTTP 500 for MES API - покажет количество неуспешных ответов от MES. Отражает общую работоспособность MES. Ярлыки: 
  - method
  - status code
  - partner login
- Number of simultanious sessions - метрика не совсем укладывается в подход RED, но может оказаться полезной: по каждому из API-сервисов можно отслеживать количество сессий, таким образом наблюдая рост нагрузки и планируя масштабирование инфраструктуры.

### 2. Серверные компоненты
- CPU % - для каждого сервиса, для каждого инстанса БД и брокера сообщений. Покажет текущую производительность. Ярлыки: 
  - instance id
- Memory Utilisation - для каждого сервиса, для каждого инстанса БД и брокера сообщений. Покажет текущую производительность. Ярлыки: 
  - instance id
- Number of connections - для каждой БД. При превышении лимита необходимо срабатывание алерта. 
- Size - для каждой БД, брокера сообщений, S3-хранилища. Необходимо срабатывание алерта при превышении объема хранилища свыше 80%.
- Number of dead-letter-exchange letters in RabbitMQ - рост этой метрики будет означать, что начались проблемы при отправке сообщений в брокере сообщений, необходимо реагирование поддержки. Ярлыки: 
  - instance id
  - error message
  - queue name
- Number of message in flight in RabbitMQ - рост этой метрики будет означать, что начались проблемы при обработке сообщений из очереди. Необходима реакция. Ярлыки: 
  - instance id
  - queue name

### 3. Бизнес-метрики
- количество текущих активных заказов - покажет текущую нагрузку на операторов, поможет планировать масштабирование
- количество "зависших" заказов - покажет заказы, обновление статуса которых не производилось дольше какого-то времени. 
- количество заказов в очереди - покажет загрузку операторов, поможет при необходимости запланировать предупреждение о временном увеличении времени обработки заказов

# Показатели насыщенности (доп. задание)
Для инстансов приложений, БД, брокера сообщений можно использовать следующую метрику: нагрузка CPU/RAM > 80% на протяжении 30 мин. Это будет означать, что система работает на "повышенных" оборотах, требуется анализ и возможное увеличение выделенных ресурсов. 
Для бд и S3-хранилища таким показателем предлагается использовать метрику объем занятого пространства превысил 80% от доступного. 
Для MES API такой метрикой может выступать среднее время, затрачиваемое на расчет: если оно превышает некий предел, значит, есть вероятность, что что-то не так. Для CRM API и Shop API по аналогии, но также можно проверять, что среднее время обработки запросов не превышает среднее время обработки запросов за последний месяц.

В качестве мер реакции предлагается срабатывание алерта с отправкой уведомления на команду поддержки и лида команды. После анализа причин срабатывания команда и лид могут принять решение, требуется ли увеличение ресурсов (в этом случае необходимо заведение тикета на devops/команду инфраструктуры). Если причина в ошибке в коде, необходимо заведение бага с необходимым уровнем и его приоритизация.
